# Nowhere Expeditions

The public campaign site and local content tools for **Nowhere Expeditions**, a [Fate Core](https://fate-srd.com/) campaign run in a West Marches style. Players form different crews for each expedition, travel through **Gates** into impossible places, and bring back discoveries that change a shared, persistent world centred on the **Island**.

**Live site:** <https://josephkhland.github.io/NowhereExpeditions/>

The repository has two halves:

- **`public-site/`**: the player-facing website. Plain HTML, CSS, and vanilla JavaScript, with no build step and no framework. It is published to GitHub Pages automatically.
- **`content-manager/`**: a small local app the GM uses to edit campaign content and write it into the site. It uses only the Python standard library, and its data lives in a local SQLite database that is never committed.

## How it fits together

```
content-manager (local, SQLite)
        │  edit Characters, Gates, Expeditions, Reports, Rules, Island Sheet
        │  tick "Published" on what players may see
        ▼
   Sync data ──► public-site/data/*.json ──► git push ──► GitHub Action ──► GitHub Pages
```

The site reads everything it shows from JSON files in `public-site/data/`. The content manager is the tool that writes those files, and it only writes records marked **Published**. Anything unpublished stays in the local database.

## Getting started

### Prerequisites

- **Python 3.9 or newer** (developed with 3.11). No packages to install.
- **Git**, to clone and push.
- Optionally **VS Code**, for the one-click task that starts everything.

### Run it locally

```powershell
git clone git@github.com:Josephkhland/NowhereExpeditions.git
cd NowhereExpeditions

# Terminal 1: the content manager
cd content-manager
python app.py            # http://127.0.0.1:8001

# Terminal 2: the public site
cd public-site
python -m http.server 8000 --bind 127.0.0.1   # http://127.0.0.1:8000
```

In VS Code you can instead run **Terminal → Run Task… → Run both**. See [RUNNING.md](RUNNING.md) for details and troubleshooting.

On first launch the content manager creates `content-manager/content.db` and fills it from `public-site/data/`. A fresh clone therefore starts with everything that is currently published. Unpublished material only exists in the GM's own copy of the database.

> Open the site through `http://127.0.0.1:8000`, not by double-clicking the HTML files. The pages load their data with `fetch()`, which browsers block for local files.

## Everyday workflow

1. Edit content in the content manager and press **Save**.
2. Tick **Published** on anything players should see.
3. Press **Sync data** to rewrite `public-site/data/`.
4. Commit and push:

   ```powershell
   git add public-site
   git commit -m "Update after session 12"
   git push
   ```

5. The **Deploy public site** Action publishes the change within a minute or two. It runs only when `public-site/` changes; it can also be started by hand from the Actions tab.

Full details, including first-time GitHub Pages setup, are in [DEPLOYING.md](DEPLOYING.md).

## Content model

| Record | What it represents | Public page |
| --- | --- | --- |
| **Character** | A player character or NPC, with an optional Fate Core sheet | `characters.html#<id>` (and `#<id>#sheet`) |
| **Gate** | A persistent location: a living dossier of what the Island knows | `gates.html#<id>` |
| **Expedition** | One planned or completed session, optionally at a Gate | `expeditions.html#<id>` |
| **Expedition Report** | The field record of an Expedition (one Expedition can have several) | Shown on its Expedition and Gate |
| **Rule** | A campaign rule or principle | `rules.html` |
| **Island Sheet** | The shared Island "character" | `island.html` |

Relationships are stored as references, and histories are derived: a Gate's history is the Expeditions that point at it, and a Character's history is the Expeditions they joined. Players can download an editable sheet from their character page, and the GM can import the file they send back. The full model, publishing rules, and the sheet workflow are described in [content-manager/README.md](content-manager/README.md).

## Working on the project

- **Read [instructions.md](instructions.md) first.** It sets the site's tone, design language, and most importantly its rule that the site is **player-facing**. Never put GM-only information (secret NPC motives, undiscovered Gate rules, unrevealed Cores) into `public-site/`.
- **Keep it simple.** The site deliberately uses static files and vanilla JavaScript so it stays easy to host and to read. Don't add frameworks or build steps without a strong reason.
- **Don't hand-edit `public-site/data/`.** Sync overwrites it. Change content in the content manager instead.
- **Run the tests** after changing the content manager:

  ```powershell
  cd content-manager
  python -m unittest discover -s tests -v
  ```

## Keeping secrets out of the repository

- `content-manager/content.db` is ignored by Git because it holds unpublished GM material. **Back it up privately**: it is not in the repository.
- `site-export/` (a full local copy made by **Export to site**) is also ignored; deployment uses `public-site/` directly.
- Anything committed stays in Git history even after it is deleted. Check `public-site/data/` before pushing if you are unsure whether something is meant to be public.
