# Nowhere Expeditions

The public campaign site and local content tools for **Nowhere Expeditions**, a [Fate Core](https://fate-srd.com/) campaign run in a West Marches style. Players form different crews for each expedition, travel through **Gates** into impossible places, and bring back discoveries that change a shared, persistent world centred on **the Outpost**, the settlement every Expeditioner works from.

**Live site:** <https://josephkhland.github.io/NowhereExpeditions/>

The repository has three parts:

- **`public-site/`**: the player-facing website. Plain HTML, CSS, and vanilla JavaScript, with no build step and no framework. It is published to GitHub Pages automatically.
- **`content-manager/`**: a small local app the GM uses to edit campaign content and write it into the site. It uses only the Python standard library, and its data lives in a local SQLite database that is never committed.
- **`discord_server/bot/`**: Vaultulation, the campaign's Discord bot, run locally by the GM with its own dashboard.

For a fuller tour of the campaign, the rules and the established lore, see [PROJECT_OVERVIEW.md](PROJECT_OVERVIEW.md).

## How it fits together

```
content-manager (local, SQLite)
        │  edit rules, lore, Gates, factions, Resources, Gear, characters, jobs, the Outpost…
        │  tick "Published" on what players may see
        ▼
   Sync data ──► public-site/data/*.json ──► git push ──► GitHub Action ──► GitHub Pages
                                                              │
                                                              └─► release vX.Y.Z + What's Changed list
```

The site reads everything it shows from JSON files in `public-site/data/`. The content manager is the tool that writes those files, and it only writes records marked **Published**. Anything unpublished stays in the local database.

Every deploy is a numbered release (`v1.0.9`). The deploy also compares the published data with the previous release and lists the new, edited and removed records on the site's **What's Changed** page (`changes.html`), down to which sections of a rule or lore entry changed. Players and reviewers can see there what to re-read.

## Getting started

### Prerequisites

- **Python 3.9 or newer** (developed with 3.11). No packages to install.
- **Git**, to clone and push.
- Optionally **VS Code**, for the one-click task that starts everything.

### Run it locally

```powershell
git clone git@github.com:Josephkhland/NowhereExpeditions.git
cd NowhereExpeditions

# Terminal 1: the content manager
cd content-manager
python app.py            # http://127.0.0.1:8001

# Terminal 2: the public site
cd public-site
python -m http.server 8000 --bind 127.0.0.1   # http://127.0.0.1:8000
```

In VS Code you can instead run **Terminal → Run Task… → Run both**, or **Everything** to start the Discord bot and its dashboard too. On Windows, `tools\start-everything.ps1` (or the desktop shortcut made by `tools\make-shortcut.ps1`) does the same in one click. See [RUNNING.md](RUNNING.md) for details, the bot's setup, and troubleshooting.

On first launch the content manager creates `content-manager/content.db` and fills it from `public-site/data/`. A fresh clone therefore starts with everything that is currently published. Unpublished material only exists in the GM's own copy of the database.

> Open the site through `http://127.0.0.1:8000`, not by double-clicking the HTML files. The pages load their data with `fetch()`, which browsers block for local files.

## Everyday workflow

1. Edit content in the content manager and press **Save**.
2. Tick **Published** on anything players should see.
3. Press **Sync data** to rewrite `public-site/data/`.
4. Commit and push:

   ```powershell
   git add public-site
   git commit -m "Update after session 12"
   git push
   ```

5. The **Deploy public site** Action publishes the change within a minute or two. It runs only when `public-site/` changes; it can also be started by hand from the Actions tab.
6. The deploy numbers the release (Patch by default; add `[minor]` or `[major]` to a commit message for a bigger step). It shows the version in the site footer and adds the release to **What's Changed**.

Full details, including first-time GitHub Pages setup and the versioning rules, are in [DEPLOYING.md](DEPLOYING.md).

## Content model

| Record | What it represents | Public page |
| --- | --- | --- |
| **Game post** | An out-of-character announcement or campaign rule; rules are ordered into learning paths | `game.html#post-<id>` |
| **Faction** | A country or power of the wider world, with its study guide of lore | `factions.html#<id>` |
| **Archive entry** | A Gate Record, an Expedition Report (session record), a Bulletin (newspaper), or a lore entry | `gates.html#<id>`, `reports.html#<id>`, `lore.html#<id>` |
| **Resource** | A material from beyond the Gates, with its Domain and Functions | `discoveries.html#resource-<id>` |
| **Spell Form** | A spell shape and the Words (Functions) it uses | `discoveries.html#form-<id>` |
| **Vocabulary** | Functions, their interactions, and Domains | `discoveries.html` |
| **Gear** | An item in the Marketplace catalogue, with price, weight and tags | `marketplace.html#gear-<id>` |
| **Expedition Pack** | A Sponsor's carrying setup and its contents | `marketplace.html#pack-<id>` |
| **Character** | A player character or NPC, with an optional Fate Core sheet, Sponsor, Packs and stash | `characters.html#<id>` (and `#<id>#sheet`) |
| **Job listing** | Work posted on the Job Board, optionally with the report of how it went | `jobs.html#<id>` |
| **Outpost Sheet** | The shared Outpost "character" | `outpost.html` |
| **Facility** | What the Outpost has, assigned to capabilities | `outpost.html#<id>` |
| **Project** | Progress tracks for Outpost and personal work | `outpost.html#<id>`, `characters.html#<id>#projects` |
| **Site settings** | Launch countdown and roadmap, Discord invite, community and sponsor credits | Overview and every footer |

Only a few relationships are structured (Job → report, participants, factions an entry is about, Resources of a Gate, stash → Gear); everything else is a `[[archive-id]]` link inside the text, so the Archive reads like a wiki. Histories are derived: a Character's history is the Jobs they joined. Players open an editable sheet from their character page, save it as a file after the session, and the GM imports the file they send back. New players can build a character the same way from **Create new character** on the Characters page. The full model, publishing rules, and the sheet workflow are described in [content-manager/README.md](content-manager/README.md).

## Working on the project

- **Read [instructions.md](instructions.md) first.** It sets the site's tone, design language, and most importantly its rule that the site is **player-facing**. Never put GM-only information (secret NPC motives, undiscovered Gate rules, unrevealed Cores) into `public-site/`.
- **Keep it simple.** The site deliberately uses static files and vanilla JavaScript so it stays easy to host and to read. Don't add frameworks or build steps without a strong reason.
- **Don't hand-edit `public-site/data/`.** Sync overwrites it. Change content in the content manager instead.
- **Run the tests** after changing the content manager or the release scripts:

  ```powershell
  cd content-manager
  python -m unittest discover -s tests -v

  # from the repository root: version numbers and the What's Changed list
  python -m unittest discover -s .github/scripts
  ```

- **Preview the next release** with `python .github/scripts/release_version.py`. It writes `public-site/version.json` and `public-site/changes.json` (both ignored by Git), so the local site shows what the next deploy will list.

## Keeping secrets out of the repository

- `content-manager/content.db` is ignored by Git because it holds unpublished GM material. **Back it up privately**: it is not in the repository.
- `site-export/` (a full local copy made by **Export to site**) is also ignored; deployment uses `public-site/` directly.
- The Discord bot's token lives in Windows Credential Manager, never in a file in the repository.
- Anything committed stays in Git history even after it is deleted. Check `public-site/data/` before pushing if you are unsure whether something is meant to be public.
